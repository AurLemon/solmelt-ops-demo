# 光热电站熔盐泵智能运营管理系统 · 板块复现项目方案书

> 本方案书以任务书《光热电站熔盐泵智能运营管理系统 板块复现》为验收依据，以《熔盐泵原理入门》十幕短课为领域知识底座，给出小组的选型、设计、分工、进度与验收映射。
> 工期：周二—周五开发，周六展示答辩。

---

## 一、项目背景与目标

### 1.1 业务背景（来自任务书 + 原理入门）

光热电站通过数万面定日镜把阳光聚焦到吸热塔，把熔盐加热后储存在熔盐罐中，再由多台熔盐泵把高温熔盐输送到蒸汽发生器发电。泵一旦故障停机，整站即停发电，因此需要一套软件系统对泵的运行数据进行 24 小时不间断采集、展示与报警。

参照真实系统「光热电站熔盐泵智能运营管理系统」，本项目要求小组借助 AI 编程工具从零实现其中四个核心板块，**界面不要求像素级一致，功能达到验收标准即可**。

### 1.2 领域知识要点（来自原理入门，作为字段/阈值/判据依据）

| 主题 | 关键事实 | 在本项目中的用途 |
| --- | --- | --- |
| 9 台泵分工 | 4 台冷盐泵（充热）、3 台热盐泵（发电）、2 台调温泵（温控） | 设备编号体系、大屏泵型分组 |
| 凝固线 | 教学值 240°C，冷罐 290°C，仅 50°C 裕量 | 运行模式派生优先级最高项 |
| 立式液下离心泵 | 电机在罐口、叶轮浸没、自灌式 | 设备属性模板的字段来源 |
| 相似定律 | Q∝n、H∝n²、P∝n³ | 电流—转速偏离判据（机械阻力变大） |
| 30 个体征 | 7 数字量（变频器状态灯）+ 23 模拟量（连续曲线） | 物模型 30 个属性的字段定义 |
| 数据单行道 | 现场只发、平台只收、网闸单向 | 数据接收接口设计只进不出 |
| 报警两条线 | 预警（嘀一声）+ 严重（响铃）；振动五路合成 | 报警引擎的阈值与判据设计 |
| 健康评分 | 五维加权：振动 30 / 轴承 25 / 定子 20 / 转速 15 / 电流 10；分段线性尺子 | （加分项）大屏健康分卡片 |
| 大屏 11 区 | 5 秒刷新、运行模式派生、数据截至到秒 | 监测大屏布局与刷新策略 |

### 1.3 项目目标

1. 四板块全部达到任务书"最低验收线"，现场跑通规定演示动作链。
2. 产出可运行系统 + 本设计方案书两份交付物。
3. 全组成员答辩时能讲清"系统怎么工作 + AI 协作过程"。

## 三、技术选型（小组集体决策）

### 3.1 选型原则（任务书 2.2）

1. 组内多数人愿意学、AI 训练数据充分的主流技术；
2. 三天工期，优先"今天决定、今晚跑出第一个页面"的成熟组合；
3. 必须有数据库（关系型即可），必须有可现场演示的界面形态。

### 3.2 最终技术栈（全组冻结）

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 全栈框架 | Node.js 24 + Nuxt 4 + Nitro + TypeScript | 单应用覆盖页面与 API，减少三天工期内的集成成本 |
| 领域组织 | Nuxt Layers | 四组各自维护完整领域目录，通过公共契约集成 |
| 数据库 | MySQL 8.4（Docker Compose） | 统一版本、账号和启动方式，避免成员环境漂移 |
| ORM | Prisma 7（多文件 Schema） | 强类型数据访问、迁移与按领域拆分模型 |
| UI | Nuxt UI + Tailwind CSS | 与 Nuxt 原生集成，快速构建后台和大屏界面 |
| 图表 | ECharts | 历史曲线、多设备对比、大屏柱状图全覆盖 |
| 校验与鉴权 | Zod + JWT + bcrypt | 固定 API 边界、token 与密码安全实现 |
| 模拟脚本 | Python 3.11+ + requests | 每 10—30 秒为 9 台设备上报，随机游走 + 偶发异常 |
| 包管理 | pnpm 11 | 单一锁文件、严格依赖与统一脚本入口 |
| 代码托管 | Gitee 私有仓库 | 国内访问稳定 |
| AI 网关 | DeepSeek HARNESS（任务书 2.3 强制） | 全组统一 |

**环境验证**：所有成员执行 `pnpm env:check`，确认 Node.js 24、pnpm 11、Git 与 `.env`；Docker Compose 是标准 MySQL 8.4 路径，无法运行 Docker 时使用原生 MySQL 8.4 兜底；Python 仅数据采集组必需。代码提交前统一执行 `pnpm pr:check`，网关连通性由每人自行验证。

## 四、系统总体架构

```
┌──────────────────────────────────────────────────────────────┐
│             Nuxt App（Nuxt UI + Tailwind + ECharts）           │
│  登录页 │ 用户/角色管理 │ 设备/产品管理 │ 数据查询 │ 监测大屏   │
└──────────────────────────────────────────────────────────────┘
                           ▲ JWT (Authorization: Bearer)
┌──────────────────────────────────────────────────────────────┐
│                       Nuxt Nitro API                           │
│   API 适配层 → 领域 Service → Prisma → Typed EventBus          │
└──────────────────────────────────────────────────────────────┘
                           ▲ HTTP POST（JSON）
┌──────────────────────────────────────────────────────────────┐
│              模拟数据脚本（Python，扮演现场采集网关）            │
│   每 10—30 秒：9 台设备 × 正常随机游走 / 偶发异常值             │
└──────────────────────────────────────────────────────────────┘
                           ▼
┌──────────────────────────────────────────────────────────────┐
│              MySQL 8.4 + Prisma（共库、领域归属）               │
│       用户/角色/菜单 │ 产品/设备/属性 │ 时序数据 │ 报警          │
└──────────────────────────────────────────────────────────────┘
```

数据流是**单行道**（原理入门幕 7）：模拟脚本只发、后端只收、前端只读，与真实电站"现场只发、平台只收"一致。

## 五、数据库设计（共库分表）

### 5.1 板块一：权限表

- `users(id, username, password_hash, role_id, status, created_at, deleted_at)` 逻辑删除
- `roles(id, name, code, remark, created_at)`
- `menus(id, parent_id, name, path, permission_code, icon, sort)`
- `role_menus(role_id, menu_id)`
- `captchas(key, answer_hash, expires_at, consumed_at)` 验证码 5 分钟有效，成功使用后立即消费，不能重复使用

### 5.2 板块二：物模型与设备

- `products(id, identifier, name, remark, created_at, updated_at)`（立式熔盐泵，标识 `Z60KbveZzXk8`）
- `product_properties(id, product_id, identifier, name, data_type, unit, category, sort)`：30 个属性
- `devices(id, product_id, device_code, name, pump_type, status, last_reported_at, created_at, updated_at, deleted_at)`
  - `status` 只有 `ENABLED`/`DISABLED`；未删除设备在最近 300 秒有成功上报即在线

### 5.3 板块三：时序与报警

- `telemetry_reports(id, device_id, reported_at, received_at, raw_json)`：一次上报一条记录
- `telemetry_values(id, report_id, property_identifier, value_number, value_boolean, value_text)`：每个属性一条值，按数据类型存储
- `device_latest_values(id, device_id, property_identifier, value_number, value_boolean, value_text, reported_at)`：由 Telemetry 写入的最新值投影
- `alarms(id, device_id, metric, threshold, actual_value, level, status, occurred_at, handled_at, handler_id)`：三项基础报警写入此表

### 5.4 板块四：只读聚合

- 大屏不拥有核心写表；只读 `devices`、`device_latest_values` 与 `alarms`，按冻结口径聚合设备数量、在线状态、运行中数量和近期报警。
- `DeviceLatestValue` 由 Telemetry 写入；Device 与 Dashboard 只读该投影，不调用 Telemetry 私有 Service。

## 六、接口约定（周三冻结）

接口的唯一说明位于 [`docs/api-contract.md`](../docs/api-contract.md)，字段 Interface 位于 `shared/contracts/`。方案书不重复维护端点表，以免出现 URL、鉴权或字段漂移。

冻结规则如下：

1. 统一前缀为 `/api/v1`；仅验证码、登录和设备数据上报匿名，其余接口都使用 JWT 与服务端权限码校验。
2. 所有响应使用 `ApiResult<T>`，分页使用 `PageResult<T>`；HTTP 中所有 ID 均为字符串，时间均为 UTC ISO 8601。
3. Auth、Device、Telemetry、Dashboard 分别只实现 `/api/v1/<domain>/*` 命名空间；领域间通过冻结投影与 Typed EventBus 协作，不直接导入其他 Layer 私有 Service。
4. 上报输入固定为 `TelemetryReportInput`：`deviceCode`、`reportedAt`、`props`。只接收存在、未删除且启用的设备，以及其物模型定义的属性和数据类型。
5. Dashboard 只读聚合；前端 30 秒轮询，基于真实 `dataUntil`/`latestReportedAt` 在超过 60 秒时显示延迟并保留最后真实值。
6. 报警状态更新接口仅是预留扩展边界；运行模式、健康评分、WebSocket 和额外运行模式端点均不属于最低验收。

## 七、四板块详细方案

### 7.1 板块一：登录与权限管理

**RBAC**：不给用户直接配权限，给用户配角色，给角色配可访问菜单。至少两种角色：管理员（看一切）与普通用户（只看业务页，看不到管理页）。

**功能清单**

- 登录页：用户名、密码（密文显示）、图形验证码（点击刷新）；后端生成 4 位随机验证码并返回图片，答案存后端 5 分钟有效、用后即删；三项均正确签发 JWT，前端存 token 跳首页；任一错误给明确提示。
- 路由守卫：未登录访问任何系统页均拦截回登录页。
- 用户管理：分页列表、按用户名搜索、新增/编辑/逻辑删除、重置密码。
- 角色管理：角色列表、增删改、给角色勾选可访问菜单。
- 权限生效：登录后按角色渲染左侧菜单；普通用户直接输入管理页地址也要被拦截（前端拦截 + 后端接口鉴权双防）。

**交付里程碑**：周二晚出第一个登录页 + token 签发；周三早接口约定文档签字后，token 机制供全组复用。

### 7.2 板块二：物模型与设备管理

**物模型概念**：给一类设备定义数据字段模板。"立式熔盐泵"产品定义会上报哪些属性（轴承温度℃、振动 mm/s、运行状态布尔等），每台具体设备都遵循该模板上报。

**功能清单**

- 产品管理：产品列表、新增产品（"立式熔盐泵"，标识 `Z60KbveZzXk8`）、物模型属性导入——读取 9 份 JSON 把 30 个属性存入属性表。
- 设备管理：设备列表（卡片或表格）、按物模型文件新增 9 台泵（编号、名称与文件一致）、编辑、逻辑删除、启用/停用。
- 设备详情：展示各属性最新一次数据值与时间，未上报显示"—"。
- 在线判定：最近 5 分钟内有数据上报视为在线，否则离线（阈值可调）。

**设备编号约定**（来自原理入门幕 1）：9 台泵编号体系沿用文件命名；判泵型看段位：01x—04x 冷盐泵、05x/06x 调温泵、WSH20 段热盐泵。

**交付里程碑**：周三晚产品+属性导入跑通；周四早 9 台设备录入并对外提供设备列表接口。

### 7.3 板块三：数据采集与数据查询

**模拟数据脚本**扮演现场采集网关，是行业测试标准做法。

**功能清单**

- 数据接收接口：后端 HTTP POST 接收统一 JSON（附录 C 格式），只接受启用设备数据。
- 数据存储：按"设备 + 时间 + 各属性值"写入时序表。
- 超限报警自动生成：入库时判定，下列任一发生即生成报警记录：
  - 驱动端轴承温度 `motor_drive_bearing_temp` > 65℃
  - 泵振动 X 轴 `pump_vibration_x` > 4.5 mm/s
  - 变频器电流 `inverter_current` > 60 A
  - 阈值存常量或配置均可，报警记录供大屏展示。
- 模拟脚本：Python 每 10—30 秒为每台设备生成一条带随机波动的数据（正常值随机游走，偶尔注入异常值）推送给后端。
- 数据查询页：选设备、监测点、时间范围 → 图表展示历史曲线，支持多设备同图对比更佳。

**进阶（可选）**：振动五路合成判据（原理入门幕 8）和完整报警状态机。它们不影响本项目最低验收，未获组长批准不安排开发。

**交付里程碑**：周四晚数据闭环跑通（脚本→入库→报警→查询曲线）。

### 7.4 板块四：监测大屏

**功能清单**（布局不必照抄，但信息密度要够、视觉要是"大屏"的样子）

- 全屏暗色页面（推荐 1920×1080 设计，自适应缩放）。
- 顶部：系统名称、实时时钟。
- 统计卡区：设备总数、在线/离线数、今日报警数、未处理报警数、运行中设备数、各泵型运行/总数等至少 6 张卡。
- 中部主图区：设备实时状态总览（在线/离线/报警色块图，或各设备最新关键指标柱状图，鼓励创意）。
- 告警列表区：滚动展示最新报警（设备、时间、内容），未处理排前面。
- 数据自动刷新：30 秒内自动拉取最新数据（轮询即可）；脚本停止推送后页面要能看出"数据停了"（数值冻结 + 延迟标识，这是原系统真实设计）。

**加分项（原理入门幕 9—10）**：平均健康分、复杂运行模式派生、30 天趋势小图。数据截至时间用于延迟标识，是最低验收的一部分；其余均须在核心链路稳定后经组长批准再做。

**交付里程碑**：周五上午大屏全链路打通；周五下午彩排演示。

## 十一、AI 协作规范（任务书 2.3）

- 全组统一使用 **DeepSeek HARNESS** 连接 AI 网关。
- 每人注册 AI 网关服务并验证配置可用。
- 把需求讲给 AI 听、验证 AI 写的代码对不对、把 AI 产出变成自己能讲清楚的东西，是本课程核心训练能力。
- 遇到任何环境报错，直接把完整报错信息贴给 DeepSeek。
