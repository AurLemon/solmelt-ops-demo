# 模块验证与组员反馈手册

这份手册用于组员完成一个模块后的自测、同组复核和跨组联调。验证必须使用真实 Seed、正式 API 和 Python 模拟器；禁止用页面静态数组、临时接口或虚构数据代替验证。

## 统一前置

每次验证前先确认：

```bash
git status --short
pnpm env:check
docker compose config --quiet
docker compose ps
pnpm db:migrate:status
```

若工作区有输出、`mysql` 服务未 `healthy`、迁移状态无法连接数据库或环境检查失败，先记录阻塞原因，不要继续猜测。启动应用后确认：

```bash
pnpm dev
curl -fsS http://localhost:3000/api/health
```

验证结束时停止本次启动的服务，保留数据库数据，执行 `pnpm pr:check` 和 `git diff --check`。若本次变更涉及依赖、公共契约或数据库迁移，必须在反馈中明确标记并交给组长处理。

## Auth：登录与权限

| 场景         | 操作                                                     | 必须观察                                          |
| ------------ | -------------------------------------------------------- | ------------------------------------------------- |
| 正常登录     | 使用 Seed 的 `admin` 和 `operator`，分别完成验证码与登录 | 两个账号均成功，返回 JWT，不暴露密码或 hash       |
| 验证码防重放 | 输入错误验证码、等待过期后输入、成功后重复提交同一验证码 | 三种情况均失败，错误信息可理解                    |
| 角色差异     | 管理员访问用户/角色/菜单；普通操作员访问相同页面和 API   | 菜单隐藏只是体验，服务端 API 也真正拒绝无权限请求 |
| 未登录访问   | 清除 Token，直接打开受保护页面并调用受保护 API           | 页面跳转登录，API 返回统一失败结构                |

反馈至少附：两个角色的操作结果、一个失败请求的状态码和响应摘要、页面或网络面板截图（不得包含 Token）。

## Device：物模型与设备

| 场景         | 操作                                                 | 必须观察                                                    |
| ------------ | ---------------------------------------------------- | ----------------------------------------------------------- |
| 基础数据     | 打开产品、属性、设备列表                             | 1 个产品、30 个属性、9 台设备，编号和单位来自老师物模型资料 |
| 设备生命周期 | 对一台设备执行编辑、停用、启用、逻辑删除             | 状态和删除标记持久化，删除后不再被当作可用设备              |
| 最新值       | 查看无上报设备和已上报设备的详情                     | 无数据显示 `—`；有数据时显示最后值与 UTC 数据时间           |
| 在线口径     | 记录最后上报时间，等待超过五分钟或使用已知旧时间查询 | 在线状态严格按 300 秒窗口派生                               |

反馈至少附：三项数量核对、一个设备生命周期前后状态、最新值时间和在线状态截图；发现编号、属性或单位不一致时，回到 `.requirements` 原始资料，不自行改名。

## Telemetry：上报、历史与报警

先确保 API 和数据库已启动；采集组按 `scripts/simulator/README.md` 创建专用 Python 虚拟环境。验证顺序：

| 场景     | 操作                                      | 必须观察                                            |
| -------- | ----------------------------------------- | --------------------------------------------------- |
| 正常上报 | 启动模拟器，观察 9 台设备持续上报         | 正式 HTTP 上报成功，形成时序记录和最新值            |
| 历史查询 | 按设备、属性和时间范围查询                | 返回真实上报点，时间为 UTC ISO 8601，分页和筛选可用 |
| 三项报警 | 产生或提交超过 65℃、4.5 mm/s、60 A 的数据 | 对应报警生成，并能被报警查询和大屏消费              |
| 停用拒收 | 停用设备后再次上报                        | 请求被拒绝，不产生新的时序、最新值或报警            |
| 停止输入 | 停止模拟器，保留页面运行                  | 不产生假数据，最后真实值保留并逐渐进入延迟状态      |

反馈至少附：模拟器启动与停止时间、一次正常上报结果、一次异常报警结果、一次停用设备拒收结果、历史查询截图或响应摘要。不得把模拟器称为页面 Mock，它是正式数据源。

## Dashboard：监测大屏

| 场景     | 操作                                   | 必须观察                                                 |
| -------- | -------------------------------------- | -------------------------------------------------------- |
| 初始展示 | 以 1920×1080 打开大屏并检查缩放        | 暗色布局、自适应、至少六张统计卡、设备状态和近期报警可见 |
| 实时更新 | 保持模拟器运行，观察不超过 30 秒的轮询 | 卡片、设备状态、最新值和报警跟随真实上报更新             |
| 延迟显示 | 停止模拟器并等待超过 60 秒             | 最后一次真实值保留，同时明确显示数据延迟/截至时间        |
| 只读边界 | 尝试通过大屏操作改变设备或报警数据     | 大屏只读，不直接写其他领域数据                           |

反馈至少附：浏览器尺寸、更新前后数据、轮询或网络请求证据、停止模拟器后的延迟标记截图。

## 跨模块联调顺序

组长按以下顺序组织一次最小闭环：

```text
Auth 登录与权限
  → Device 读取 1 个产品、30 个属性、9 台设备
  → Telemetry 模拟上报、入库、报警、历史查询
  → Dashboard 实时更新、报警展示、停止后的延迟标记
```

任何一环失败，反馈中标记“阻塞于哪个领域、使用了哪个接口、最后一个成功数据是什么”，由对应领域处理；不要让下游组临时绕过接口或写假数据。

## 组员反馈模板

每个任务完成后在 PR 或小组协作消息中粘贴：

```text
【模块】auth / device / telemetry / dashboard
【负责人与分支】姓名，feat/<domain>
【任务】一句话说明本次实现
【提交】commit hash
【环境】Node/pnpm、Docker、数据库状态；不填写密码、Token 或 JWT_SECRET
【操作】按顺序列出命令、页面操作或 API
【预期】冻结契约要求的结果
【实际】实际观察到的结果
【证据】截图、响应摘要、日志时间；隐藏敏感信息
【状态】PASS / PARTIAL / BLOCKED
【未通过项】复现步骤与完整错误
【需要协作】需要哪个领域通过哪个接口、事件或 Contract Change 配合
```

完成者先自测，同组成员再按本手册复核，最后由新的只读 AI 会话 Review diff；反馈必须能让另一位成员在相同环境中复现，而不是只写“测试通过”。
